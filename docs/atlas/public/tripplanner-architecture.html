Trip Planner: architecture atlas

A group trip planner with no accounts. The organiser creates a trip and shares capability links: an organiser link, an edit link and a view-only link. Everyone plans day by day with autosave, editing indicators and conflict handling. The stack is a React SPA and a Hono API on Cloudflare Workers with Neon Postgres, built spec-first and running on free tiers.

Business context

From specs/goal-spec.md (v0.5). Problem: when several people plan a trip, ideas scatter across chats, notes and spreadsheets, and one person ends up collecting everything by hand. Answer: one shared plan that anyone can open from a link. Nobody signs up.

Goals & success metrics (goal §4, §11)

  • G1: create a trip in under 1 minute. G2: share by link with no accounts. G3: everyone edits day plans. G4: suggest places and earlier trips.
  • Metrics: create and share in ≤ 1 minute · ≥ 80% of trips edited by 2+ people, counted anonymously through trip_contributors (Q25) · ≥ 1 suggested place per trip · zero data loss · $0 hosting.
  • Constraints: free tiers only, a 3-month pilot, a tight budget and timeline. Out of scope: accounts, bookings, payments, live cursors.

Security & privacy model

Capability links instead of accounts

  • Every trip has 3 codes, each 32 random bytes encoded as 43-character base64url (randomToken(), BR1). Guessing one is infeasible.
  • One indexed lookup across all three columns gives the trip and the role (middleware/tripAccess.ts). An unknown code returns 404, never 401, so trip existence never leaks.
  • The role is checked on the server for every route (requireRole, which runs before body validation). The UI only hides controls.

Personal data

  • Organiser email: only HMAC-SHA256(EMAIL_HMAC_SECRET, email) is stored (BR11). The address is used once to send, never logged or returned.
  • Contributor metric: a per-trip HMAC of the display name, never the name itself (BR18).
  • Recovery always answers 202 with the same body, is rate-limited, and sends email in the background (BR12). This prevents email enumeration.

Transport & browser

  • CSP is generated at build time (apps/web/tooling/securityHeaders.ts): the inline theme script is pinned by hash, connect-src is limited to the API origin, and frame-ancestors 'none'.
  • Referrer-Policy: no-referrer on the web app and the API, so codes don't leak to outside links. CORS allows a single origin with no cookies, so no CSRF surface.
  • Responses to routes with a code are no-store; the published trip (E16) is no-cache.

Abuse & configuration

  • Per-IP limits per minute come from Workers Rate Limiting bindings; hourly limits use DB counters (rate_counters).
  • lib/config.ts fails closed. Production refuses fake providers, log-only email, non-HTTPS origins and placeholder or short secrets.
  • Logs record the route pattern, never the raw path, so access codes, emails and day text never reach them (requestContext.ts).

Layers

  • Shared: date rules in AoE, slugs, text cleaning, the permission matrix (packages/shared/test).
  • API: integration tests use app.request() against a truncated tripplanner_test database. Concurrency is covered (two parallel saves → exactly one 200 and one 409), as are email privacy, ranking and config.
  • Web: the autosave state machine with fake timers; page tests drive a small in-test fake fetch (src/test/fakeApi.ts) instead of MSW.
  • E2E: e2e/playwright.config.ts boots wrangler dev and Vite against tripplanner_e2e with fixed seed codes.

Bugs the tests caught

  • A trip deleted while open stayed visible, because the 404 was ignored when cached data existed.
  • The "email sent" note vanished once ?created was dropped, which wiped the navigation state.
  • WCAG AA contrast failures: teal-600 buttons and slate-500 text.
  • Un-publishing was delayed by the 60-second cache on E16.
  • LIKE wildcards weren't escaped in Explore search.
  • Flaky E2E: substring text matches, and Radix toasts appearing twice.
